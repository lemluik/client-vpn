# Стенд автопереключения входов (Д2-18)

Мерит **поведение** ядра при отказе узла, а не валидность конфига: `xray run -test`
принимает блок наблюдателя с незнакомыми полями (Go молча пропускает их), поэтому
проверка синтаксиса не доказывает, что автопереключение работает.

Секретов нет: узлы входа — локальные SOCKS-релеи, ссылки и ключи не нужны.

## Состав

| Файл | Роль |
| --- | --- |
| `probe_target.py` | HTTP-цель наблюдателя; пишет каждое обращение ядра в `run/hits-<порт>.jsonl` и отвечает 204 |
| `socks_relay.py` | Узел входа. Режим читается из файла-флага на каждое подключение: `ok`, `refuse` (сразу закрыть), `blackhole` (принять и молчать — зависание), `drop` (порт недоступен) |
| `run_stand.py` | Собирает конфиг, поднимает ядро и релеи, шлёт пробы, впрыскивает отказ, разбирает журнал ядра и печатает итог |

## Требования

- Python 3.11+, сторонних пакетов не нужно.
- Ядро: `assets/xray/xray.exe` (переопределяется переменной `XRAY_BIN`).
- Порты стенда `19080`, `19081`, `19091`, `19092`, `19098` свободны. Они нарочно
  не пересекаются с точками входа клиента (`10808`/`10809`) и с чужими стендами
  на `180xx`. Стенд гасит процессы только по этим портам, поэтому ядро живого
  клиента не задевает.
- Запускать можно рядом с подключённым клиентом: системный прокси стенд не трогает.

## Запуск

```
python test/stand/run_stand.py --variant fixed --fail-mode blackhole --duration 120 --fail-after 25
```

Основные параметры:

| Параметр | Смысл |
| --- | --- |
| `--variant` | Форма блока наблюдателя: `current` (боевая до правки), `fixed` (принятая), `minimal`, `no_subjects`, `serial`, `prefix`, `burst_current`, `burst_fixed` |
| `--fail-mode` | `drop` — пакеты теряются, `blackhole` — соединение принято и молчит, `refuse` — немедленный отказ, `none` |
| `--fail-after` | Секунд до впрыска отказа (`-1` — не впрыскивать) |
| `--fail-node` | Какой узел ломать: `A`, `B` или `carrying` — в момент впрыска взять узел, который сейчас несёт трафик (балансировщик ставит трафик на узлы недетерминированно, а мерить переход надо с рабочего узла) |
| `--recover-after` | Через сколько секунд после впрыска вернуть узел A в строй |
| `--fail-b-after` | Через сколько секунд после впрыска сломать и узел B (проверка утечки напрямую) |
| `--probe-interval` | Интервал проб наблюдателя, строка длительности (`10s`) |
| `--strategy`, `--tolerance` | Стратегия балансировщика и порог прилипания |
| `--endpoint` | Цель наблюдателя; по умолчанию локальный счётчик |

## Что печатает итог

- проб отправлено и сколько прошло;
- **обращений ядра к цели наблюдателя** — ноль означает, что наблюдатель не
  запущен и переключения не будет;
- строки журнала ядра с тегом выхода (`A` = `cvpn-proxy`, `B` = `cvpn-proxy-2`),
  отдельно до и после впрыска;
- время перехода на узел B в секундах;
- строки с уходом напрямую (`cvpn-direct`) — их должно быть ноль;
- при `--recover-after` — вернулся ли трафик на узел A;
  при `--fail-b-after` — сколько проб прошло при двух мёртвых узлах.

Журналы и конфиг прогона остаются в `test/stand/run/` (каталог в git не попадает).
